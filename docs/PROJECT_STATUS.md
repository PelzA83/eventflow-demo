**Дата фиксации:** 2026-11-11  
**Этап:** рабочая демонстрационная версия — гостевой RSVP и кабинет организатора подключены к Supabase

> Этот документ — основной handoff-контекст для разработчиков и ИИ-помощников, подключающихся к публичной демоверсии. При расхождении с кодом сначала проверяйте актуальные файлы репозитория и фактическое состояние Supabase. Не считайте планы реализованными функциями.

## 2. Что уже реализовано

### Гостевая страница (index.html)

- Персональная страница приглашения открывается по URL с параметром token.
- Данные мероприятия, группы и гостей загружаются из Supabase через RPC get_invitation(p_token text).
- Гость может выбрать один из ответов: «Приду» / «Не смогу».
- Повторное нажатие на выбранный ответ снимает выбор; отправка сбрасывает статус в pending.
- Поддерживается изменение ранее отправленного ответа.
- Отправка выполняется через RPC submit_rsvp(...).
- Ответ сохраняется в Supabase и переживает обновление страницы.
- Приглашение работает с частичным изменением ответа: обновляется ответ выбранного гостя, а не вся группа.

**Исправленный критический дефект:** кнопки содержали data-value="yes" / data-value="no", но JavaScript читал selected.value. Из-за этого мог отправляться pending, хотя интерфейс показывал успешную отправку. Исправлено чтение на selected.dataset.value.

### Кабинет организатора (organizer.html)

- Данные не являются статической заглушкой: кабинет получает мероприятие, статистику и список гостей из Supabase через RPC get_organizer_dashboard().
- Отображаются название мероприятия, дата, время, место проведения (или сообщение, что место пока не указано), статистика и список гостей.
- Добавлены фильтры списка: «Все», «Придут», «Не придут», «Ожидают».
- Фильтрация работает на загруженных данных на стороне браузера.
- Выполнено визуальное обновление: расширенная область кабинета, шапка мероприятия, карточки статистики, панель гостей, статусы и адаптация для мобильных экранов.
- Демонстрационный код входа 1234 сохранён.

**Важно:** код 1234 — только декоративный демонстрационный gate, а не аутентификация и не защита данных. Не использовать для реальных мероприятий или персональных данных.

## 3. Проверенный демонстрационный сценарий

Тестовое мероприятие использует вымышленные данные:

- Название: «Свадьба Александра и Марии».
- Дата и время: 12 июня 2027 года, 16:00.
- Часовой пояс: Europe/Moscow.
- RSVP deadline: 29 мая 2027 года.
- Группа: «Семья Ивановых».
- Гости: Александр Иванов, Мария Иванова, Максим Иванов.

Проверено вручную 2026-11-11:

1. Выбор «Приду» отправляется и сохраняется после обновления страницы.
2. Повторный выбор снимается; после отправки сброса и обновления страницы статус остаётся ожидающим.
3. Ответ можно изменить с «Приду» на «Не смогу», изменение сохраняется.
4. Ответ другого гостя корректно отображается в кабинете организатора.
5. Кабинет показывает согласованные с базой значения: 3 гостя всего, 1 подтверждение, 1 отказ, 1 ожидает ответа.
6. Фильтры списка гостей работают после жёсткого обновления страницы.

На момент последней проверки:
- Александр — «Не смогу» (declined);
- Мария — «Приду» (confirmed);
- Максим — ожидает ответа (pending).

Не включайте персональный токен приглашения в документацию, публичные примеры или сообщения коммитов. Для повторной проверки используйте актуальную тестовую ссылку, предоставленную владельцем проекта.

## 7. Автообновление и нагрузка — принятое решение

**Важно: автообновление каждые 10 секунд пока НЕ реализовано.** Это согласованное направление, а не текущая функция.

Решение:
- Демоверсия: планируется polling каждые 10 секунд, чтобы при презентации клиент быстро видел новые ответы.
- Коммерческая версия: ориентир 60 секунд по умолчанию либо событийное обновление через Supabase Realtime.
- Неактивная/скрытая вкладка: polling следует приостанавливать.
- При возвращении на вкладку: сразу выполнять проверку свежих данных.
- Не допускать параллельных одинаковых запросов; сохранять выбранный фильтр.
- Пока polling не добавлен, не утверждать, что кабинет обновляется автоматически: сейчас данные обновляются при загрузке/перезагрузке страницы.

Polling не увеличивает размер HTML/JS или ZIP-архива. Он увеличивает количество чтений из Supabase, сетевой трафик и нагрузку на обработку. Число приглашений само по себе не равно числу активных кабинетов: нагрузка зависит прежде всего от количества одновременно открытых кабинетов.

Ориентировочно при непрерывно открытой вкладке:
- каждые 10 секунд — 8 640 запросов в сутки на один кабинет;
- каждые 60 секунд — 1 440 запросов в сутки на один кабинет.

Это число запросов, а не расчёт стоимости. Реальные расходы зависят от тарифа Supabase, объёма ответа, активных пользователей, лимитов и других операций. Не обещать конкретную стоимость без актуальных тарифов и измерений.

## 8. Требования к персональному обращению и импорту списка гостей (новое, запланировано)

Эти требования согласованы владельцем проекта 2026-11-11. **Пока не реализованы**; не описывать их как готовые функции.

### Персональное обращение к гостю

В русскоязычном приглашении обращение рядом с кнопками ответа не должно автоматически строиться как «Имя Фамилия». Нужен отдельный настраиваемый формат обращения для каждого гостя:

- Уважительное мужское: «Уважаемый Александр Сергеевич».
- Уважительное женское: «Уважаемая Мария Петровна».
- По имени: «Максим» — типичный вариант для ребёнка.
- Уважительное обращение допустимо и к подростку/взрослому, если организатор хочет подчеркнуть уважение или статус.

Правила реализации:
- Хранить имя, фамилию и отчество как отдельные данные гостя.
- Не выводить фамилию в обращение по умолчанию.
- Не пытаться надёжно определять возраст или форму обращения только по имени.
- Для каждого гостя предусмотреть явный формат/форму обращения: «Уважаемый», «Уважаемая» или «Только имя». При выборе уважительного варианта использовать имя + отчество; если отчество отсутствует, показать предупреждение и дать организатору исправить данные либо явно подтвердить допустимый вариант.
- Показывать организатору итоговую строку обращения в списке гостей/редактировании, чтобы он видел, что именно увидит приглашённый.
- Использовать одно и то же персональное обращение на гостевой странице рядом с кнопками RSVP и в соответствующих представлениях кабинета организатора.
- Фамилия остаётся в списке организатора для различения однофамильцев и идентификации гостей.

### Групповое обращение к семье/группе

Дополнительно согласован сценарий обращения ко всей семье одним приглашением. Это не набор индивидуальных обращений с повторяющимся «Уважаемый/Уважаемая», а единое групповое обращение:

«Уважаемые»

Александр Иванович  
Мария Николаевна  
Максим

Правила:
- Групповое обращение выбирается на уровне приглашения/группы гостей.
- Заголовок группового обращения — «Уважаемые».
- Ниже выводятся участники этой группы отдельными строками.
- Для взрослых и подростков, которым организатор хочет выразить уважение, выводить имя + отчество.
- Для ребёнка или гостя, которого принято называть только по имени, выводить только имя.
- Фамилии остаются в административном списке организатора, но не обязаны показываться в тексте обращения.
- Организатор должен иметь возможность проверить состав и порядок участников, а также индивидуальный формат имени каждого участника до отправки/публикации приглашения.
- Не определять автоматически, кому выводить отчество: формат задаётся организатором для каждого участника.
- Если у участника выбран формат с отчеством, но отчество не заполнено, показать предупреждение до подтверждения.

Пример семейной группы:
- Александр Иванович
- Мария Николаевна
- Максим

### Импорт списка гостей

В кабинете организатора предусмотреть действие «Загрузить список гостей» с импортом табличного файла. Целевые форматы: Excel (.xlsx) и CSV.

Предлагаемые поля шаблона:
- Группа
- Имя
- Фамилия
- Отчество
- Форма обращения (значения: «Уважаемый», «Уважаемая», «Только имя»)

Пример:
- Семья Ивановых | Александр | Иванов | Сергеевич | Уважаемый
- Семья Ивановых | Мария | Иванова | Петровна | Уважаемая
- Семья Ивановых | Максим | Иванов | [пусто] | Только имя

Ожидаемый UX импорта:
1. Кнопка загрузки файла в кабинете.
2. Предварительный просмотр распознанных строк до записи в базу.
3. Проверка обязательных полей, неизвестных значений формы обращения, отсутствующего отчества при уважительном обращении и возможных дубликатов.
4. Понятные ошибки с номером строки и возможностью вернуться к таблице.
5. Подтверждение импорта организатором.
6. После импорта новые гости появляются в нужных группах и получают персонально сформированное обращение.

Правила безопасности и целостности данных:
- Повторная загрузка того же файла не должна молча создавать дубликаты.
- Импорт не должен случайно сбрасывать уже сохранённые RSVP-ответы. Изменение данных существующего гостя и добавление новых гостей должны быть разделены/подтверждены.
- Не принимать произвольные SQL/формулы как команды; импортировать только значения ячеек.
- Для массового импорта разработать серверную проверку и авторизацию организатора, не полагаться только на проверки в браузере.
- Привязка гостя к группе должна быть однозначной; поведение для неизвестной группы должно быть показано до подтверждения.

При реализации сначала согласовать шаблон таблицы и правила распознавания дубликатов. На первом этапе не менять существующую рабочую RSVP-логику без необходимости.

- создание/редактирование нескольких мероприятий из кабинета;

- полноценный аудит безопасности.

Приоритет ближайшей демо-итерации:
1. По отдельному согласованию добавить polling 10 секунд в organizer.html, только для активной вкладки; не менять index.html.
2. Проверить, что фильтр сохраняется после обновления данных, а ошибки сети не ломают кабинет.
3. Проверить поведение после ответа гостя в другом браузере/устройстве.
4. Подготовить демо к показу потенциальному клиенту.

Перед переходом к коммерческой версии:
1. Спроектировать multi-tenant модель (несколько организаторов/мероприятий).
2. Сделать полноценную авторизацию и авторизацию на уровне мероприятия.
3. Пересмотреть RPC и RLS с учётом изоляции данных.
4. Определить стратегию обновления (Realtime или polling с адаптивным интервалом).
5. Проверить тарифы, лимиты, объём хранения, резервное копирование и мониторинг.
6. Развернуть production отдельно от публичной демоверсии.
